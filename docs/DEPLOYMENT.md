# Shiftspace deployment and recovery

This configuration targets a small Virginia pilot of 1–5 stores and up to 100 staff total. It has not been deployed publicly. The local workload and CI verification use synthetic accounts and separate disposable databases. Hosting charges, a private backup bucket, a domain, incident contacts and a first-store payroll review still require an operator to supply real values.

## Hosting

`render.yaml` defines one paid Standard web service in Virginia (2 GB RAM), one persistent 10 GB volume at `/var/data`, and a private Redis-compatible Key Value service with `noeviction`. The web service uses two Gunicorn worker processes and four threads per worker. The verified Linux workload measured 430.5 MB peak web-process RSS, excluding the backup/supervisor processes; a 512 MB web plan would leave too little headroom. The proposed larger plan is configuration only and does not establish real hosted capacity. Review its current pricing before deployment. See [Render compute plans](https://render.com/docs/compute-plans). A disk permits multiple processes in one instance; it prevents horizontal instances and zero-downtime deploys. Plan short deployment maintenance periods. Database migrations run in the start command while the disk is mounted, before web workers start. They never run in ordinary request handling or individual Gunicorn worker startup. See [Render persistent disks](https://render.com/docs/disks).

Render terminates public TLS and forwards requests to Gunicorn over the internal listener. Enable the app's explicit one-hop `TRUST_PROXY` only behind that trusted edge, restrict access to the listener, and set `PUBLIC_ORIGIN` to the canonical HTTPS domain; Render's `RENDER_EXTERNAL_URL` supplies the default domain when no explicit override is set. The app validates the host, uses Secure/HttpOnly/SameSite cookies and HSTS, and rejects malformed canonical origins. Custom-domain DNS and certificates are configured in the Render dashboard. See [Render web services](https://render.com/docs/web-services) and [custom domains](https://render.com/docs/custom-domains).

Use the Blueprint's manual deployment setting until production checks and the operator review are complete. Validate without creating resources:

```text
python -m scripts.validate_blueprint
```

## Secrets and first startup

Set these privately in the hosting environment:

| Setting | Purpose |
| --- | --- |
| `FLASK_SECRET_KEY` | New random signing key, generated by the Blueprint; retain through normal restarts |
| `MFA_ENCRYPTION_KEY` | Independent Fernet key for encrypted authenticator secrets |
| `BACKUP_ENCRYPTION_KEY` | Independent URL-safe base64 key containing 32 random bytes for AES-GCM backups |
| `BACKUP_BUCKET` | Owned private S3 bucket in a separate failure domain |
| `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` | Dedicated minimum-permission bucket identity |
| `PUBLIC_ORIGIN` | Canonical HTTPS origin, or the platform-provided default origin |
| `RATELIMIT_STORAGE_URI` | Internal Key Value connection supplied by the Blueprint |

Retain the MFA and backup encryption keys in a separate access-controlled secret manager. Database backups do not include environment secrets. Losing the backup key makes backups unusable; losing the MFA key prevents accounts from verifying their authenticators. Changing the signing key invalidates all signed sessions, store cookies and invitation links. Never commit keys, enter them as CLI arguments, or paste them into logs.

The production launcher rejects disabled secure cookies, in-memory or disabled rate limiting, disabled privileged MFA, disabled payroll review, invalid HTTPS origins, and hub/store databases outside `DATA_ROOT`. Before opening the listener, it creates an encrypted pre-migration backup of existing data, upgrades the hub and every registered store, and completes an off-host backup/download/restore check. A missing store, failed migration or unsuccessful off-host backup prevents startup. Do not seed the demo in production.

Create the initial administrator explicitly through the protected hosting shell:

```text
python -m flask --app run create-admin
```

The command prompts for credentials. For an owner-only hub account, use the trusted `set-role USERNAME owner` command after account creation. Sign in over HTTPS, enroll an authenticator, save recovery codes, create the owned stores, and use each store's **Staff access** page for manager permissions and staff recovery links. Bootstrap and emergency owner recovery still require trusted server access; routine staff administration uses the app.

## Monitoring

`/healthz` reports process liveness. `/readyz` returns 200 only when the hub and every registered store are at schema head, shared rate-limit storage is reachable, recent off-host backup and restore verification both exist, and no maintenance marker is active. Each dependency remains independently visible as a boolean. Missing store files are opened read-only and never recreated. Production backups expire for readiness after twice the configured backup interval; malformed, non-finite or far-future timestamps cannot report healthy.

Structured production request logs contain an endpoint, method, status, duration, request ID and store code. They omit query strings, request bodies, reset links, employee names, passwords, MFA codes, cookies and IP addresses. Gunicorn access logs omit paths as well. Connect the host's logs and resource metrics to an operator-owned alert destination. Run an external uptime check from a separate host:

```text
python -m scripts.monitor_probe --origin https://YOUR-CANONICAL-DOMAIN
```

Alert on failed readiness, repeated 5xx responses, stale backups, disk space below 20%, memory pressure and unavailable Key Value. The probe emits status and duration only and exits nonzero when unhealthy. A monitor script and endpoint do not establish a running external monitor or configured alerts. Confirm a real alert delivery before inviting staff.

## Backups

The supervised backup process runs daily by default; `BACKUP_INTERVAL_SECONDS` can reduce the recovery-point window. During a snapshot the application returns temporary maintenance responses, and the backup code holds SQLite write locks on the hub and all registered stores. This produces one coherent registered-store inventory. It uses SQLite's native backup API, validates integrity and foreign keys, records SHA-256 checksums, and encrypts the entire archive with authenticated AES-GCM.

Every cycle uploads the encrypted file with bucket-side encryption, downloads the stored object, compares its checksum, decrypts it, restores every database into a fresh scratch directory, and checks the restored inventory. Only then does it atomically replace the readiness status. Failed copies and restore checks preserve the previous successful status. Two local encrypted snapshots remain; configure versioning, restricted access and lifecycle retention on the off-host bucket. Verify that the backup identity can upload and download the configured prefix while public bucket access is blocked.

The launcher supervises both Gunicorn and the backup process. Unexpected backup-process exit stops the web process instead of silently disabling backups. Graceful SIGTERM during snapshot or offline initialization unwinds the owned maintenance marker. SIGKILL or a host failure can leave a marker: stop the service, verify its recorded process is absent and no migration/backup is running, then remove only that stale marker through trusted administration before restarting. The application never automatically deletes another process's maintenance marker.

## Recovery drill

Download an encrypted object through your private bucket access. Restore with the independently retained key in `BACKUP_ENCRYPTION_KEY` and a new directory:

```text
python -m scripts.backup_store_bundle restore --source backup.enc --destination NEW-RECOVERY-DIRECTORY
```

An existing destination is refused. Failed authentication, truncation, checksum mismatch, unsafe paths or mismatched store inventory cannot overwrite live data. The restored layout is `hub.db` plus `stores/GENERATED-KEY.db`. Before switching traffic, retain the current volume, point a stopped isolated app at the recovered hub/store paths, use the same retained MFA key, run migrations explicitly if required, and verify owner access, each store's schedules, punches, payroll snapshots, pictures and audit records. Rotate the signing key for a security incident so restored sessions cannot resume automatically. Reconcile work recorded after the snapshot before staff use the recovered app; the last successful snapshot bounds possible lost work.

Record the object ID, snapshot time, successful database counts, integrity checks, restored business records and elapsed recovery time in the operator's incident system. The automated download/restore check verifies recoverability of the archive; it does not measure restoration of DNS, secrets, alerts or a replacement paid service. Rehearse a full isolated recovery with those real resources before the first store pilot. Database-native backups are the recovery source; [Render warns against disk-snapshot recovery for custom databases](https://render.com/docs/disks#restoring-a-custom-database).

## Workload verification

```text
# Windows: real two-process Waitress workload, with no Redis/TLS production claim
python -m scripts.production_workload --report artifacts/local-production-workload.json

# Linux: disposable loopback Redis database 15 plus real two-worker Gunicorn and TLS
python -m scripts.production_workload --redis-uri redis://127.0.0.1:6379/15 --report artifacts/production-workload.json
```

The workload migrates six disposable databases, creates five stores and 100 synthetic staff, and runs 24 concurrent clients through real CSRF-protected sign-in, private schedules, shared chat and clock-in/out. It checks actual worker process IDs, shared-Wi-Fi sign-in, per-store/per-person privacy, concurrent duplicate clock-in safety, zero unrequested payroll records and full table/row equality after an encrypted six-database restore. The Linux mode adds a trusted disposable TLS certificate, Secure cookies, the production proxy path and a shared Redis chat-limit check across both workers. CI runs Linux mode with an actual Redis service container and saves the non-sensitive result as an artifact.

This is a finite loopback workload. It does not prove 100 simultaneous active users, a long soak, memory headroom on a particular paid plan, hosted network latency, external S3 availability, regional failover or a legal payroll approval. Measure memory/CPU on the chosen host during a supervised pilot and adjust the compute plan before broad rollout. The disk architecture remains one server instance; moving beyond this scale requires a separately reviewed shared-database design.
